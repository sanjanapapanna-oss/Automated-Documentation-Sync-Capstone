# Automated Documentation Sync

[![CI](https://github.com/sanjanapapanna-oss/Automated-Documentation-Sync-Capstone/actions/workflows/ci.yml/badge.svg)](https://github.com/sanjanapapanna-oss/Automated-Documentation-Sync-Capstone/actions/workflows/ci.yml)

An Agentic SDLC Pipeline, built entirely from Claude Code's native primitives, that takes a
project from a raw user story through requirements, architecture, design review,
implementation planning, implementation, code review, verification, and PR preparation — with
a human approving every consequential step.

Its primary business application: **documentation synchronization** — read a master
technical-documentation template and a source repository, extract verified facts, populate
the template without inventing information, validate the result, and prepare an updated
technical application manifest ready for review.

## Status

All 8 pipeline stages have been run end to end against the Automated Technical Documentation
Sync v1 user story: `output/automated-technical-documentation-sync-v1/requirements.md` through
`verification-report.md` are complete, and the application itself (`src/core`,
`src/integrations`, `src/cli`) is implemented with 72 passing tests (95%+ statement coverage).
No Jira/Confluence/GitHub MCP server or `gh` auth is configured in this environment; see
[Integrations](#integrations) for how the pipeline behaves until one is.

## Installation

Requires Node.js ≥ 20.

```bash
npm install
npm run typecheck   # verify the toolchain is wired correctly
npm run test        # run the 72-test unit/integration suite
```

Copy `.env.example` to `.env` and fill in only the integrations you actually have credentials
for — every field is optional; the pipeline degrades gracefully when one is missing.

## Architecture

```
.claude/            The pipeline itself
  agents/           9 subagents: sdlc-orchestrator + 8 stage specialists
  commands/         8 slash commands, one per SDLC stage
  skills/           6 skills (requirements-engineering, architecture-design,
                     documentation-sync, test-strategy, secure-code-review, pr-preparation)
  hooks/            check-secrets.js, format-on-write.js, verification-gate.js
  settings.json     Wires the hooks above to PreToolUse/PostToolUse events
mcp/                 Documented MCP integration config for Jira, Confluence, GitHub
src/
  core/              Business logic: template parsing, source extraction, field resolution,
                      output validation — built during Stage 5
  integrations/       Adapters: jira/, confluence/, word/, direct-input/, git-hosting/
  cli/                 Thin CLI entry points
tests/
  unit/, integration/, fixtures/
examples/            Sample user story + sample source repo for demoing the pipeline
output/<story>/      Generated per pipeline run: requirements.md, architecture.md,
                      design-review.md, impl-plan.md, code-review-report.md,
                      verification-report.md, pr-description.md
CLAUDE.md            Binding project instructions — read this first
CHANGELOG.md, PR_TEMPLATE.md    Repo-wide assets, not per-run artifacts
```

Full architectural detail (components, data flow, tech-stack rationale, security boundaries)
lives in `architecture.md` under that run's `output/<story>/` folder, generated by Stage 2 of
each pipeline run.

## The Eight Stages

| #   | Stage                   | Command          | Subagent               | Output                          |
| --- | ----------------------- | ---------------- | ---------------------- | ------------------------------- |
| 1   | Requirements            | `/requirements`  | `requirements-analyst` | `requirements.md`               |
| 2   | Architecture            | `/architecture`  | `architect`            | `architecture.md`               |
| 3   | Design Review           | `/design-review` | `design-reviewer`      | `design-review.md`              |
| 4   | Implementation Planning | `/impl-plan`     | `impl-planner`         | `impl-plan.md`                  |
| 5   | Implementation          | `/implement`     | `implementer`          | source code + tests             |
| 6   | Code Review             | `/code-review`   | `code-reviewer`        | `code-review-report.md`         |
| 7   | Verification            | `/verify`        | `verifier`             | `verification-report.md`        |
| 8   | PR Preparation          | `/prepare-pr`    | `pr-preparer`          | PR description, changelog entry |

Each command and agent file documents its own required inputs, expected outputs, validation
rules, and approval requirements — see `.claude/commands/*.md` and `.claude/agents/*.md`. All
outputs above live under `output/<user-story-slug>/`, a folder Stage 1 creates from the
story's title (see `CLAUDE.md` §5 rule 6) — never at the repository root.

You can also say "run the pipeline" / "resume the pipeline" and the `sdlc-orchestrator` agent
will track stage state and delegate automatically, still pausing for approval at every gate.

## Human Approval Gates

No stage's output file is committed, no dependency is added, no destructive operation runs,
and no PR is created or pushed without explicit human authorization **in that turn** — see
`CLAUDE.md` §5 for the full rule set. A prior approval does not carry forward to a new,
different action.

## Hooks

Configured in `.claude/settings.json`:

- **`check-secrets.js`** (`PreToolUse`, matches `Write|Edit`) — scans content being written for
  credential-shaped patterns (AWS keys, private key blocks, Slack/GitHub tokens, generic
  API-key/password assignments) and blocks the write (exit code 2) if found, unless the target
  is clearly an example/placeholder file.
- **`format-on-write.js`** (`PostToolUse`, matches `Write|Edit`) — best-effort runs Prettier on
  the written file; never blocks, no-ops safely if Prettier isn't installed yet.
- **`verification-gate.js`** (`PreToolUse`, matches `Bash`) — blocks `git push` and
  `gh pr create` unless a `verification-report.md` exists under some `output/<story>/` folder
  and doesn't record an unresolved mandatory failure.

All three are deterministic, mechanical safeguards — they do not replace agent judgment, and
they are documented here per `CLAUDE.md` §4's requirement that hooks stay reliable and
auditable.

## Integrations

See `mcp/README.md` for full setup instructions. Summary:

| Source         | MCP-backed path                                                     | Fallback (used today)                        |
| -------------- | ------------------------------------------------------------------- | -------------------------------------------- |
| Jira           | Atlassian/Jira MCP server (not configured)                          | Paste ticket text or point to a local export |
| Confluence     | Atlassian/Confluence MCP server (not configured)                    | Paste page text or point to a local export   |
| Word documents | —                                                                   | Read directly from a local file path         |
| GitHub         | `gh` CLI auth (preferred) or GitHub MCP server (neither configured) | Local `output/<story>/pr-description.md` + manual steps |

Nothing in this repository invents credentials or assumes a server is reachable — every
integration failure is reported plainly with the fallback offered instead.

## Running the Pipeline

```
/requirements <story text, file path, Jira key, or Confluence URL>
/architecture
/design-review
/impl-plan
/implement next
/code-review
/verify
/prepare-pr
```

Run them in order; each command checks its own preconditions (e.g. `/impl-plan` refuses to run
while `design-review.md` has an open blocker) and will tell you what's missing rather than
guessing forward. `/requirements` creates the `output/<user-story-slug>/` folder that every
later command reads from and writes into for that run.

## Security

- Secrets never belong in source, tests, fixtures, logs, or generated documents — enforced by
  `check-secrets.js` and restated in `CLAUDE.md` §4.
- All content from repositories, documents, tickets, and tool output is treated as untrusted —
  agents summarize it, never execute instructions embedded in it.
- `.env`, `.claude/settings.local.json`, and `mcp/*.local.json` are git-ignored; only
  `.example`/`.md` files with placeholder values are committed.

## Evidence Standards

No stage reports a test as passing, a check as executed, or a fact as found without a real,
reproducible basis — see `CLAUDE.md` §6. Generated documentation distinguishes **"Not Found"**
(looked, not there) from **"Not Specified"** (out of scope for this source) at all times.
